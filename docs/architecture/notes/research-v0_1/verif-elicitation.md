- VERIFICADO — La especificación vigente de MCP es la revisión **2026-07-28** (marcada como "Current"). Fuente: https://modelcontextprotocol.io/specification/versioning ("The **current** protocol version is **2026-07-28**").

- VERIFICADO — La spec vigente incluye **elicitation** (servidor solicita información adicional al usuario a través del cliente). Fuente: https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation ("a standardized way for servers to request additional information from users through the client during interactions"). Soporta dos modos: **form** (datos estructurados con JSON Schema plano) y **url** (interacción fuera de banda que NO pasa por el cliente).

- VERIFICADO — Elicitation se **introdujo en la revisión 2025-06-18**. Fuente: https://modelcontextprotocol.io/specification/2025-06-18/changelog ("Add support for **elicitation**, enabling servers to request additional information from users during interactions", PR #382). El modo URL se introdujo en 2025-11-25 (nota en la página de elicitation: "URL mode elicitation is introduced in the `2025-11-25` version"). En 2026-07-28 el mecanismo de transporte cambió: `elicitation/create` ya no es una petición server→client, sino que viaja dentro de un `InputRequiredResult` (patrón Multi Round-Trip Requests) y el cliente reintenta la petición original con `inputResponses`. Fuente: https://modelcontextprotocol.io/specification/2026-07-28/changelog (cambio mayor 7, SEP-2322).

- VERIFICADO (con matiz importante) — Sobre CÓMO el cliente presenta la solicitud: la spec **NO mandata un modelo de interacción específico** ("Implementations are free to expose elicitation through any interface pattern that suits their needs—the protocol itself does not mandate any specific user interaction model"). Lo que sí exige (MUST, form mode): el cliente "MUST provide UI that makes it clear which server is requesting information", "respect user privacy and provide clear decline and cancel options" y "allow users to review and modify their responses before sending". Las acciones de respuesta se definen en términos de acción humana ("Accept: User explicitly approved and submitted... Example: User clicked Submit"), y el diagrama de flujo muestra User→Client ("Present elicitation UI / User provides requested information"). Fuente: https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation

- NOT FOUND — La spec **no contiene ninguna prohibición explícita** de que el cliente/modelo genere la respuesta de una elicitation de modo form sin intervención humana. Los MUST sobre UI implican presentación al usuario, pero "user approval controls" es solo SHOULD ("Clients **SHOULD** implement user approval controls"). Conclusión para la revisión arquitectónica: en **form mode**, elicitation como canal de aprobación humana infalsificable depende de la implementación del cliente, no de una garantía de la spec. En **URL mode** sí hay garantías más fuertes: el cliente "MUST NOT open the URL without explicit consent from the user", "MUST show the full URL to the user for examination before consent" y "MUST open the URL... in a secure manner that does not enable the client or LLM to inspect the content or user inputs" (ej.: SFSafariViewController sí, WkWebView no) — es decir, la interacción sensible ocurre fuera del alcance del modelo por diseño. Fuente: https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation (Security Considerations / Safe URL Handling).

- VERIFICADO — Advertencias de seguridad de la spec sobre elicitation: servidores "MUST NOT use form mode elicitation to request sensitive information such as passwords, API keys, access tokens, or payment credentials" y "MUST use URL mode" para eso; servidores MUST vincular la elicitation a la identidad cliente/usuario; MUST NOT incluir credenciales/PII en la URL ni URLs pre-autenticadas; el servidor MUST verificar que quien abre la URL es el mismo usuario que originó la elicitation (mitigación de phishing/account-takeover descrita en detalle); clientes MUST NOT pre-fetch la URL. Fuente: https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation

- VERIFICADO — La spec define **anotaciones de tools** (`annotations` en la definición de Tool; interfaz `ToolAnnotations` con `title`, `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) y su carácter es de **hints NO confiables, no garantías**. Página de Tools: "For trust & safety and security, clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers" (https://modelcontextprotocol.io/specification/2026-07-28/server/tools). Schema oficial: "all properties in ToolAnnotations are **hints**. They are not guaranteed to provide a faithful description of tool behavior... Clients should never make tool use decisions based on ToolAnnotations received from untrusted servers" (https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2026-07-28/schema.ts).
